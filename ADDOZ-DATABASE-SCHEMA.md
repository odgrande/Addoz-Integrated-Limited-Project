# ADDOZ Database Schema

This document outlines the core data models for the ADDOZ platform. The database uses PostgreSQL (via Neon Serverless) and Drizzle ORM.

## Better Auth Tables

These tables are required by the `better-auth` library to handle authentication and user sessions.

- **`user`**: Stores core user identity (id, name, email, role, etc.). `email` is unique; `role` is the `user_role` PostgreSQL enum (`candidate`, `employer`, `admin`) and defaults to `candidate`.
- **`session`**: Tracks active user sessions.
- **`account`**: Links external OAuth providers to users.
- **`verification`**: Handles email/passwordless verification tokens.

## ADDOZ Core Entities

### User Profiles

- **`candidate_profile`**: 
  - **Description**: Stores candidate-specific information.
  - **Relationships**: One-to-One with `user`, Many-to-One with `location`.
  - **Fields**: headline, experience, etc.

- **`employer_profile`**: 
  - **Description**: Stores employer-specific information.
  - **Relationships**: One-to-One with `user`, Many-to-One with `company`.
  - **Fields**: contactName.

### Business Entities

- **`company`**: 
  - **Description**: Represents an employer's company.
  - **Fields**: slug, name, logo, website, description.
  
- **`job`**: 
  - **Description**: A job posting created by an employer.
  - **Relationships**: Many-to-One with `company`, `category`, `location`.
  - **Fields**: slug, title, type, workplace, level, experience, salary min/max, summary, skills (array), status (Active, Draft, etc.).

- **`job_application`**: 
  - **Description**: A candidate's application to a specific job.
  - **Relationships**: Many-to-One with `job`, `candidate_profile`, `resume`.
  - **Fields**: stage (Applied, Shortlisted, Interview, Hired, etc.), appliedAt.

- **`resume`**: 
  - **Description**: A file uploaded by a candidate.
  - **Relationships**: Many-to-One with `candidate_profile`.
  - **Fields**: fileName, fileSize, url.

- **`saved_job`**: 
  - **Description**: Jobs bookmarked by candidates.
  - **Relationships**: Many-to-One with `candidate_profile`, `job`.
  - **Primary Key**: Composite (`candidateId`, `jobId`).

- **`job_alert`**: 
  - **Description**: Saved search alerts for candidates.
  - **Relationships**: Many-to-One with `candidate_profile`, `category`, `location`.

- **`notification`**: 
  - **Description**: In-app notifications for users.
  - **Relationships**: Many-to-One with `user`.

### Taxonomy / Metadata

- **`category`**: Job categories (e.g., Design & Creative).
- **`location`**: Geographical areas (e.g., Victoria Island).
- **`skill`**: Specific skills (e.g., React, Figma).

## Indexes & Constraints

- Primary keys are UUIDs generated by `defaultRandom()` (except for Auth tables and taxonomies which use text IDs or slugs).
- Foreign Key constraints ensure referential integrity between applications, jobs, profiles, and users. All currently use PostgreSQL's restrictive `NO ACTION` delete/update behaviour.
- Slugs on `job`, `company`, `category`, and `location` are unique.
- `candidate_profile.user_id` and `employer_profile.user_id` are unique, enforcing one profile per user per profile type.
- `saved_job` uses the composite primary key `(candidate_id, job_id)`.
- `job_application` uses the unique index `(candidate_id, job_id)`, preventing a candidate from applying to the same job twice.
